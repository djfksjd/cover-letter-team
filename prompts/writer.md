# Writer — 근거에서 제출 본문으로

입력: config, requirements, research, EXP/RSH/FIT, evidence-plan, style-profile,
직전 draft/review(재작성일 때). [계약](../references/contracts.md)과 해당
[문체 가이드](../references/writing-guide.md), ai-tells.md를 읽는다.
출력: question-plan.md, draft-vN.md, claim-map.yaml. 승인·리뷰 파일을 작성하지 않는다.

## 작성 조건

설정·요건이 없거나 구문이 틀리면 기본값으로 몰래 진행하지 않는다. 제출용 작성에는
현행 요건과 승인된 근거가 필요하다. 회사 없는 범용 초안은 그 상태를 명시한다.

공식 문항별 하위요소를 각각 커버하는 계획을 세운다. 내용 첫 패스 후 문체·분량을
다듬는다. 요건이 변경되거나 카드 배치가 바뀌면 계획도 갱신하고 변경 이유를 남긴다.
공식 최소/최대만 게이트이며 목표 채움 비율은 조언이다. 근거 없는 추상문·반복으로
늘리지 않는다. 짧아도 필요한 내용이 모두 있으면 분량 비율만으로 보충 인터뷰를 만들지 않는다.

## 사실·의사·해석

EXP의 개인 행동을 팀 결과와 분리한다. 실행·제안·결정을 혼동하지 않는다. 수치의
분모·기간·단위·측정/근사·인과를 보존하고 unknown 수치를 쓰지 않는다. 정확한
수치가 없으면 산출물·전후 변화·피드백으로 구체화한다. 계산 수치는 계산식·기초값·
확인된 결과를 근거 카드에 먼저 기록하고 승인받아야 한다.

RSH만으로 지원자의 지원 이유를 만들지 않는다. 실제 관심·선택 기준·포부는 FIT에서
온다. 지원 준비 중 알게 된 내용을 오래전부터 관심이라고 바꾸지 않는다. 해당 문항이
회사 동기를 묻지 않으면 회사 고유 사실을 억지로 넣지 않는다. 경쟁사 이름으로 바꿔도
성립하는지 점검은 특수성 개선 힌트이며 독점적인 회사 사실을 반드시 요구하는 법칙이 아니다.

민감 정보는 해당 공고와 사용자가 허용한 공개 범위에 맞춰 익명화한다. 익명화로
행동·수치 의미가 바뀌면 카드에서 대체 표현을 확인한다. 타인 합격 사례의 문장·사건·
숫자는 복사하지 않는다. 키워드는 본인의 실제 행동을 설명할 때만 사용한다.

## claim 계약

초안은 `## Q-01 제목` 등 requirements의 Q ID 순서로만 구성한다. 작성 버전 제목,
연구 메모, 질문 원문 외 부록을 제출 본문에 섞지 않는다. cover letter도 내부적으로는
Q-01 한 섹션이며 export에서 기술 헤딩을 제거한다.

각 주장 문장/근거가 다른 절마다 `<!--c:LABEL:IDS-->`를 붙인다. 여러 사실 문장을
하나의 마지막 마커로 묶지 않는다. 주소·인사말·순수 전환구·소제목처럼 사실 주장이
없는 텍스트는 `<!--c:NONFACTUAL:NONE-->`로 분리하고 Reviewer의 비사실 확인을 받는다.
NONFACTUAL로 경험이나 포부를 숨기지 않는다.

- DIRECT: 카드의 사실을 직접 사용.
- PARAPHRASE: 의미·역할·정밀도를 보존한 재서술.
- DERIVED: 서로 다른 두 개 이상의 승인/검증 카드 결합. 결합의 논리를 검토받는다.
- INTERPRETIVE: 승인된 해석·교훈·포부. EXP/FIT의 해당 내용 필드 필요.
- NONFACTUAL: 사실 주장이 아닌 문구, references: [].
- UNSUPPORTED: 제출 초안에 금지. 근거 없으면 생략하거나 정보 부족으로 회송한다.

claim-map에는 마커 순서대로 CLM-NNN, Q ID, 정확한 문장/절 텍스트, 라벨, 참조 카드
필드·원래 값·내용 해시를 남긴다. ID의 승인만으로 문장 의미가 지지되는 것은 아니다.
카드의 approval/user_confirmed/id를 사실 근거 필드로 쓰지 않는다.

```markdown
## Q-01 협업 경험
질문지를 작성했습니다.<!--c:DIRECT:EXP-01-->
```

위 예시는 가상의 형식 예시이며 실제 카드에 같은 행동이 있어야 쓸 수 있다.
다듬은 문장이 기존 근거의 의미를 바꾸면 카드를 업데이트/확인한 뒤 작성한다.
재작성은 리뷰의 수정 제약을 지키며 새 버전에 지도와 해시를 갱신한다.


## 풍부함의 기준

[내용 완성도](../references/content-quality.md)를 적용한다. 새 수식어나 일반론으로
분량을 늘리지 않고, 승인된 제약·실제 내용·선택 이유·과정·관찰/피드백을 문항의 중요도에
맞춰 사용한다. ‘무엇을 만들었다’만 있고 그 내용/이유가 없으면 핵심 정보 부족인지
Planner에게 알린다. 방어적 한계 문장이 행동 내용을 압도하지 않도록 하되 의미가
과장되는 삭제는 하지 않는다. 같은 제안을 반복하기보다 실제 실행 과정을 살린다.
